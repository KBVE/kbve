# KBVEData plugin consolidation (3d) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: superpowers:subagent-driven-development. **EXECUTE IN A UE-ENABLED ENV** — this touches the UE build graph AND the CI dispatch manifest; both must be validated by a real compile + a CI matrix dry-run, neither of which is possible in the authoring env. Do NOT merge on static verification alone.

**Goal:** Collapse the six standalone DB plugins (`KBVEItemDB`, `KBVENPCDB`, `KBVEQuestDB`, `KBVEMapDB`, `KBVESpellDB`, `KBVEProfessionDB`) into a single `KBVEData` plugin with one module per DB — the "one `KBVE<T>` plugin, modularity within" structure — without changing any consumer's `#include`s or `Build.cs` module deps.

**Architecture — why it's feasible:** UE resolves module dependencies by **module name**, not owning plugin. If each DB's `Source/KBVE<DB>/` module directory moves *unchanged* under `KBVEData/Source/KBVE<DB>/`, the module name stays `KBVE<DB>`, so every consumer `Build.cs` dep (`"KBVEMapDB"`, …) and every `#include "KBVE<DB>Database.h"` keeps resolving. Only the **plugin** layer changes: six `.uplugin`s → one `KBVEData.uplugin` listing all modules, and consumers' `.uproject` swaps the six plugin entries for one.

**Recommended phasing (do NOT big-bang all 6):**
- **Phase 1 (this plan):** consolidate the 3 lean, codegen-simple plugins — `KBVEProfessionDB` (8 files), `KBVESpellDB` (12), `KBVEMapDB` (14) ≈ 34 files — into `KBVEData`. Proves the entire mechanic (moves + merged uplugin + uproject + codegen OUT_DIR + nx + manifest + CI matrix) on a reviewable/reversible surface.
- **Phase 2 (follow-up):** migrate the 3 large plugins (`KBVEItemDB` 45, `KBVENPCDB` 35, `KBVEQuestDB` 23) into the now-proven `KBVEData` using the identical steps.

**Tech Stack:** UE5 plugin/module structure (`.uplugin`, `.Build.cs`), `git mv`, Node codegen (`gen-*-uecpp.mjs` OUT_DIR), nx `run-commands` targets, CI dispatch manifest (`.github/ci-dispatch-manifest.json` via `ci-manifest-sync.yml`) + matrix (`.github/scripts/ue-plugin-matrix.mjs`).

Manifest is regenerated by `ci-manifest-sync.yml`. So after moving files, the manifest MUST be re-synced (its generator globs plugins/reads metadata — verify the generator picks up the multi-module `KBVEData` and drops the three old entries).
- `ci-unreal-plugins.yml` `discover` job runs the matrix; each matrix entry builds one plugin (`plugin_name`/`plugin_path`) with its `dependency_plugins`. A multi-module `KBVEData` = one entry that must build all its modules — VERIFY the build step compiles every module of the plugin (not just a single-module assumption).

## RISKS (why this is UE-env-only)

- **No local UE compile:** module-graph correctness (a moved `.Build.cs`, a plugin-dep the merged uplugin missed, a `LoadingPhase` mismatch) surfaces only in a UE build.
- **CI-manifest entanglement:** the build matrix is manifest-driven; if the manifest generator doesn't cleanly produce one multi-module `KBVEData` entry (and drop the three), CI either skips the plugin or references dead paths. Verifiable only by running the sync + matrix (Task 4) AND the actual build job.
- **Multi-module build assumption:** `ci-unreal-plugins.yml`'s per-entry build step may assume one module per plugin; a `KBVEData` with 3 modules must be confirmed to build ALL modules. If not, the build workflow itself needs a change (out of this plan's scope — flag it).
- **version.toml / release tracking:** collapsing 3 `version.toml`s into one changes per-plugin version tracking; confirm no release/publish flow keys off the old plugin dirs.
- **Reversibility:** `git mv` history is preserved, but a merged-then-reverted consolidation is a noisy round-trip — do NOT merge until all three real gates are green.
